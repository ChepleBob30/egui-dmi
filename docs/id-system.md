# 组件编号分配系统说明

本文对应的实现文件：`src/ui/id.rs`（注册表核心）、
`src/ui/components.rs`（组件的登记过程）、`demo/dmi_gallery/src/main.rs`（使用示范）。
设计依据：`build_docs/plan/dmi.md` 第 1.2 节。

---

## 1. 系统要解决的问题

编号系统只做一件事：**给大模型（DMI）一个稳定、可读、可以逐个列出来的名字，
用来指代界面上的每一个组件**。egui 每一帧都重新构建界面，组件本身没有
跨帧保持的身份。这个系统在"组件"和"egui 的临时身份"之间加了一张登记表：

- **登记时机**：组件调用 `show()` 显示时自动登记或刷新，使用方不需要手动操作；
- **编号含义**：整数编号代表一个组件；带小数的编号代表复合组件里的子项；
  0 号是系统专用编号，不分配给任何组件；
- **两条必须始终成立的规则**：
  1. 名称不同，一定分配新编号。即使两次调用发生在同一个 egui 身份上
     （例如同一块调色板分别用于改文字颜色和改背景颜色），也会得到两个编号；
  2. 名称相同，一定沿用原来的编号。即使界面布局变化导致 egui 身份改变、
     即使程序运行了很多帧，也绝不会重复登记。

## 2. 数据结构总览

```text
REGISTRY: OnceLock<Mutex<DMIRegistry>>     进程内唯一的一份数据
DMIRegistry
 ├─ records:        Vec<DMIRecord>         按分配先后排列的条目列表
 ├─ reused:         HashMap<String, DMIId> 名称到编号的对应表（名称是唯一判断依据）
 ├─ located:        HashMap<DMIId, Id>     编号到最近一次 egui 身份的对应表（用于定位组件）
 ├─ next_major:     u32                    下一个可用的主编号（从 1 开始，0 已留给系统）
 ├─ minor_counters: HashMap<DMIId, u32>    每个父编号已经分配过多少个子编号
 ├─ revision:       u64                    版本号，只有真正新增条目时才加一
 └─ snapshot:       Arc<Vec<DMIRecord>>    条目列表的只读副本，新增条目时重新制作
```

说明：`OnceLock` 是"只允许初始化一次"的容器，`Mutex` 是互斥锁，
保证多线程访问同一份数据时不会互相踩踏；`Arc` 是引用计数共享指针，
多个读取者共享同一份只读副本而不复制内容。

### 2.1 编号类型 `DMIId { major, minors, depth }`

编号由主号加一串小数组成，`DMI_MAX_DEPTH = 4` 表示小数最多 4 段，
因此 `1`、`1.2`、`1.2.3.4` 都能表达。`depth` 记录 `minors` 数组里
实际有效的小数段数。这里使用固定长度数组而不是 `Vec`，
因为 `DMIId` 会被用作哈希表的键，而且每帧的登记过程都会接触它，
固定数组可以让它保持可复制、可哈希、可比较，并且完全不产生堆分配。

| 方法 | 作用 | 这样设计的原因 |
| --- | --- | --- |
| `DMIId::SYSTEM`（常量） | 系统专用的 0 号 | 计划文档规定 0 号留给系统层接口；它还用作"上级"字段的默认值，表示"没有上级"，这样就不必使用 `Option` 类型。 |
| `DMIId::new(major)` | 用主号构造编号 | 编译期函数，登记过程没有额外运行开销。 |
| `is_system()` | 判断是否为 0 号 | 未注册的组件需要一个明确的"没有编号"返回值，用它表示比 `Option` 更直接，字段类型也保持统一。 |
| `is_root()` | 判断是否为不带小数的编号 | 取代过去"小数段等于 0"的判断写法，语义更清楚。 |
| `child(minor)` | 在编号末尾追加一段小数，返回 `Option` | 子编号继承父编号的主号，小数逐段追加（`1` 追加成 `1.1`，再追加成 `1.1.1`）；已经满 4 段时返回 `None`。小数只是位置信息，不是身份，追加不会改变前面的段。 |
| `level(index)` | 读取第 `index` 段小数 | 超出有效段数时返回 0；供排序、名称拼接和序列化使用，外部代码不需要直接操作数组。 |
| `From<u32>` | 整数直接转成编号 | 在测试和 JSON 场景里写 `1` 就等价于 `DMIId::new(1)`，减少重复代码。 |
| `Display` | 显示为 `1`、`1.2`、`1.2.3` | 与计划文档里 JSON `target_id` 的写法完全一致。注意：两层以上的小数在 JSON 里必须写成字符串（如 `"1.1.1"`），因为 `1.1.1` 不是合法的 JSON 数字。 |

### 2.2 类型枚举 `DMIWidgetKind` 与 `as_str()`

七种组件类型做成一个枚举。用枚举而不是任意字符串的原因是：类型集合是固定的，
拼错的、不存在的类型根本无法进入系统；`as_str()` 输出与计划文档一致的
`"button"`、`"select"` 等字符串，只在展示和序列化的时候才转换成字符串，
存储和比较始终保持类型安全。

### 2.3 条目类型 `DMIRecord` 与显示格式

每条记录包含五部分：编号、类型、（上级编号与触及方式）、名称、功能映射。
其中"上级"是一个二元组：上级组件的编号，加上"从上级组件触及本组件的方式"
（例如先左键点击父下拉菜单展开，再左键点击选项）；
根组件的上级固定为 `(0, Direct)`，`Direct` 表示"没有上级、直接可见"。
功能映射是"功能名称对应哪些触及方式"的列表，在登记时写入，
同名重复登记时以第一次写入的为准。
`Display` 输出形如：

```text
(1, "select", (0, Direct), "theme_selector", [("expand", [LeftClick, Hover])])
```

这种格式人可以直接阅读，大模型也可以直接解析，将来还能逐行还原成结构化数据。

## 3. 复用机制（核心）

### 3.1 名称是唯一判断依据

复用判断只看名称：对应表就是一个 `HashMap<String, DMIId>`。
这个结论经过了两次收紧：

1. 最早的版本同时看 egui 身份和名称。实际测试发现了两类故障：
   第一，egui 的自动身份由控件在界面中的位置推算出来，界面内容一变
   （日志多了一行、下拉展开收起、文字长短引起布局移动），位置身份就变了，
   同一个组件被误认为新组件而重复登记；
   第二，注册表自己的显示行也是组件，也参与登记，于是"表变长导致行变多、
   行变多又让表更长"，条目数量失控。详细经过见
   `build_docs/changelog/2026-11-14-performance-fix.md`。
2. 第一次收紧把"身份"和"定位"分开：有名称的只看名称，没名称的按 egui 身份；
   第二次收紧（严格声明制）删掉了"没名称按 egui 身份"这条退路：
   没有声明名称和功能的组件一律不登记。

这正对应计划文档里的那句话：egui 身份的意义是让 DMI 定位组件，
名称的意义是帮助 DMI 分配编号。

- **名称即身份**：界面布局怎么变化都不影响，名称 `theme_selector`
  永远对应同一个编号。位置变化只更新"定位表"里的记录；
- **定位表**：`located` 保存每个编号最近一次出现时的 egui 身份，
  将来 ACCESS 类接口需要操作真实控件时，从这里查回组件当前的位置。

### 3.2 `allocate()`：根组件的登记

登记过程（`DMIRegistry::allocate`，公开入口 `allocate()`）依次做四步：

```text
1. 严格校验：名称不能为空；功能映射可以为空，不为空时每一项的功能名不能为空、
   触及方式列表不能为空、列表里不允许出现 Direct、同一组件内功能名不能重复。
   任何一项不满足，直接返回 SYSTEM 占位值，什么都不写入。
2. 按名称查复用表。查到：只更新定位表，返回已有编号，
   条目列表、版本号、只读副本全都不动。
3. 查不到：取下一个主编号，构造记录（上级固定为 (0, Direct)），
   调用 push_record 写入。
4. 把名称与新编号写入复用表，把新编号与本次 egui 身份写入定位表。
```

三条设计理由：

- **查到就立刻返回**是复用的硬性要求：重复调用只刷新定位、绝不改动列表，
  "每一帧都在重复更新列表"的问题从结构上杜绝；
- **没有自动名称**：功能映射是 DMI 操作组件的依据，名称缺失或功能缺失的
  组件信息不可信，宁可少一条记录，也不要一条说不清是谁的记录；
- **同一个 egui 身份配两个名称得到两个编号**自然成立：两个名称就是
  复用表里的两个键，互不遮挡。计划文档"一块调色板同时改文字颜色和背景颜色
  会得到两个编号"的场景就是靠这条实现的。

### 3.3 `allocate_child()`：子项的登记

与根组件登记基本相同，有四点差别，每一点都有理由：

- **名称必须完整**（"父名称_子项名称"的形式）：子项总是带着父名称登记的，
  因此同样不受布局位置变化影响，下拉展开收起、选项顺序调整都不会造成重复；
- **触及方式必填且不能是 `Direct`**：`Direct` 专用于根组件，
  子项必须说明"从父组件怎么触及到我"；
- **父编号必须已经在表里**：防止先登记子项、父项却不存在造成的孤儿记录；
- **子编号按出现顺序分配**：`minor_counters` 给每个父编号单独计数，
  第一次出现的子项拿到 `父编号.1`，第二个拿到 `父编号.2`。
  已经登记过的子项命中复用，所以往列表中间插入新选项，
  不会导致后面的旧选项全体改号。
  计数键是任意编号，因此"子项再有子项"（`1.1.1`）不需要任何额外代码；
- **深度保护**：追加第 5 段小数时 `child()` 返回 `None`，
  此时明确拒绝：调试版本直接指出问题，发布版本返回 SYSTEM 且不写入任何记录。
  宁可拒绝，不做静默截断。

### 3.4 `push_record()`：唯一允许列表变长的出口

```rust
records.push(record);  revision += 1;  snapshot = Arc::new(records.clone());
```

"写入条目、版本号加一、重新制作只读副本"三件事锁在同一个私有方法里：
复用路径不可能误改版本号，任何列表增长必然伴随版本变化。
因此版本号可以放心地作为"界面需不需要重建显示"的唯一依据。
只读副本在每次新增时整体重建一次，读取方永远免费（见 3.7）；
代价是每次真正新增要复制一遍列表，当前条目规模（几十到几百条）完全可接受。

### 3.5 `locate()`：定位通道

`located` 是"编号到最近一次 egui 身份"的表，每次登记（无论新旧）都会更新。
方向选择的原因：同一个 egui 身份可以合法对应多个编号（调色板的场景），
反过来"一个编号"只对应一个 egui 身份，这个方向的信息是无损的，
也正是将来操作真实控件所需要的。只要组件还在被绘制，`locate()` 就能查到它现在的位置。

### 3.6 `name_of()`：按编号查名称

子项登记需要用"父名称_选项文本"拼出完整名称，而组件手里只有父编号，
所以提供按编号查名称的接口。它线性扫描条目列表，
只在真正新增子项前调用一次，不在每帧的复用路径上，当前规模够用；
将来成为性能热点时，可以再加一张"名称到编号"的反向索引表。

### 3.7 `list_id()` 与 `registry_revision()`：读取端零成本

- `list_id()` 返回 `Arc<Vec<DMIRecord>>`：只复制一个引用计数，不复制条目本身。
  注册表面板因此可以每帧读取而不会产生大量内存复制；
- `registry_revision()` 返回版本号：面板先读版本号（开销极小），
  版本没变就继续使用自己缓存的显示内容，连副本都不取；版本变了才重建。
  这样"库里命中复用就不动列表"加上"界面版本不变就不重绘"，
  两层规则一起把每帧开销压到几次加锁和哈希查找。

## 4. 组件的登记过程（`src/ui/components.rs`）

- **`.dmi_name(text)`**：七种组件统一的名称声明方法。
  名称是复用判断的唯一依据，必须交给使用组件的人控制；
- **`register()` 登记函数（私有）**：`show()` 结束时统一走这里。
  声明过名称就调用 `allocate()` 登记；没声明名称就返回 `DMIId::SYSTEM`，
  组件照常显示但不进注册表。每个组件的出口只有一行调用；
- **`DMIUpdate.id` 就是登记结果**：调用方用 `id.is_system()`
  即可判断自己忘了声明名称；
- **`DMISelect::individual_ids()` + `sanitize_name()`**：开启后，
  弹出层里本轮绘制过的每个选项，都会以"父名称_清洗后的选项文本"登记为子条目。
  `sanitize_name()` 把选项文本转成小写字母、数字、下划线组成的片段，
  对齐计划文档 `theme_selector_light` 的命名样式。
  选项文本就是名称的一部分，所以复用只看文本，与控件位置无关；
- **`DMISelect::grouped(label, current, groups)`**：分组下拉。
  分组本身登记为子条目（编号 `父编号.序号`），
  分组内每个选项再登记为下一层（编号 `父编号.序号.序号`），
  名称依次是"父名称_分组名"和"父名称_分组名_选项名"。
  分组模式自动启用小数编号。收起、展开、布局变化都不造成重复；
- **`DMIRadio::group(name)`**：单选框是计划文档点名的"一次产生多个组件"的工具。
  组名第一次出现时通过 `allocate()` 得到一个统一的整数父编号
  （操作这个编号就代表操作整组），每个成员再通过 `allocate_child()`
  得到小数子编号，名称是"组名_选项文本"。
  `DMIUpdate.id` 返回成员自己的子编号（能看出点的是哪一个），
  父编号留在表里供整组操作。计划文档的两种编号方式在这里同时成立。
  设计取舍：`DMIRadio` 保持单控件的使用方式，组语义只加一个方法，
  不引入新的组件类型；
- **`DMIUpdate::new` / `DMIUpdate::from_parts`**：纯数据构造函数。
  `from_parts` 是私有方法，只接收 `&Response` 并取出两个布尔值，
  所以从结构上就不可能把 `Response` 带出 `show()`，也不可能漏掉 `id` 字段。

## 5. 并发与生命周期

- `REGISTRY` 用 `OnceLock<Mutex<DMIRegistry>>` 做成**进程内唯一的一份数据**，
  跨帧、跨面板持续存在，满足"程序启动时保存一个列表"的要求。
  不放在 `egui::Context` 里，因为测试里每帧可能使用不同的 Context 实例，
  而且 Context 自带数据在程序重启时的存取行为不受本库控制；
- `with_registry()`：所有公开方法统一通过它加锁访问。
  如果某个线程在持锁期间崩溃（Rust 里叫 panic），锁会进入"中毒"状态，
  此时仍然取回锁内的数据继续使用：登记操作全部是往列表末尾追加，
  单次崩溃不会让已有数据损坏，不应该因此永久停掉整个编号功能；
- **确定性**：编号的分配顺序就是各组件第一次被绘制的先后顺序。
  同一份程序只要界面顺序不变，编号序列每次运行都完全一致，
  这是大模型可以放心记住"上次看到的编号"的前提。

## 6. 完整流程实例（demo 的外观下拉）

```text
第 1 帧  DMISelect 声明名称 "theme_selector" 并开启选项独立编号，弹出层关闭。
         show → register → allocate(egui身份X, Select, "theme_selector", 空功能表)
         → 复用表查不到 → 分配编号 1，写入记录、版本变为 1。
         （表内：(1,"select",(0,Direct),"theme_selector",[])）

用户点开下拉，第 2 帧 弹出层画出"浅色"和"深色"两个选项。
         allocate_child(egui身份A, "theme_selector_浅色", 父=1, LeftClick, 空功能表)
         → 查不到 → 分配 1.1；同理"深色"分配 1.2。版本变为 3。
         注册表面板发现版本变化 → 重建三行显示内容。

第 3 帧到第 n 帧 反复绘制、滚动、切换外观，egui 身份不断变化。
         三个名称全部命中复用表 → 列表不增长、版本不变，
         面板连只读副本都不再读取，只用缓存。

用户选择"深色" → 选中值写回，DMIUpdate.changed 为 true，
         DMIUpdate.id 是父编号 1。

将来 DMI 发送 {"target_id": 1.2} 的命令
         → 用 list_id() 查到名称和类型
         → 用 locate(1.2) 拿到该选项当前的 egui 身份 → 操作真实控件。
```

编号机制支持三层及更深的编号（上限 4 层），命名规则是
"父完整名称 + 下划线 + 本项名称"逐段拼接。第一个实际用例是
`DMISelect::grouped`（demo 的"场景预设"）：分组得到 `父编号.序号`，
分组内选项得到 `父编号.序号.序号`，例如 `5.1.2`。

## 7. 已知边界与后续方向

| 边界 | 目前的代价 | 触发改造的条件与方案 |
| --- | --- | --- |
| 只读副本在每次新增时整体重建 | 新增一条要复制一遍列表，开销与条目总数成正比 | 条目达到数千条时，改成分段共享的链表式结构或增量副本 |
| 未声明名称的组件不受 DMI 管理 | 编号为 SYSTEM，接口无法操作它 | 接入 ACCESS 接口前，逐个核对界面组件是否都声明了 `dmi_name`（demo 已全部声明） |
| `name_of()` 逐条线性查找 | 只在新增子项前调用，不在每帧路径上 | 成为热点时，增加"名称到编号"的反向索引表 |
| 条目只增不删 | 界面永久移除的组件，记录留在表里 | 将来给每条记录加"最后一次出现的帧"标记，定期清理长期未出现的条目 |
| 嵌套层数上限 4 层 | 第 5 层被明确拒绝（调试版直接指出，发布版返回 SYSTEM） | 确有更深需求时调大 `DMI_MAX_DEPTH` 即可，机制本身不用改 |

## 8. 测试与机制的对应关系

- `named_identity_survives_egui_drift`：对应 3.1 的"名称即身份"与 3.5 的定位刷新；
- `repeated_allocation_does_not_grow`：对应 3.2 的"命中复用就不动列表"（十次调用只有一条记录）；
- `child_ids_follow_parent`：对应 3.3 的子编号复用与追加结构；

  连续 300 帧混合绘制命名控件与匿名标签，验证列表只增长命名控件那几条；
- `test_mutex`：多个测试共用同一份全局表时，让涉及数量断言的测试排队执行，互不干扰。
