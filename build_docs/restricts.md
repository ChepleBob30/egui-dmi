# 开发规范

1. 每次开工前，与用户确认实现方法、修改的文件、拿不准的实现细节这几点，待用户批准后再施工。
2. 每个方法、变量、字段等内容的命名不超过30个字符。
3. 为每一个方法和实现特定功能（e.g. 一个实现从指定路径获取并加载图片的方法中，你需要标出其文件查找与读取功能、适应图片尺寸功能等）的代码块添加不超过中文40字（英文按照中文翻译即可）的双语注释。
4. 尽可能减少临时存储型字段，多用变量处理，出现性能问题除外。
5. 在开始每一次任务前，你必须捋清项目结构，确认各个文件的代码风格，保持代码一致性。
6. 尽可能集中功能，不要将功能拆得特别散，方法少写几个。
7. 如果要创建文档，请放置在build_docs/changelog目录下。
8. 完成任务后，用人类能够理解的语言撰写一份修改报告，说明你改了哪几个文件，加了什么方法，对什么东西做了修改。
9. 无论做什么事情，一定要保留回退改动的余地。
10. **不要使用缩写。**
11. **不要替用户提交代码。**
12. 每次完成改动后，及时在build_docs/changelog添加新文件以及更新build_docs/structure.md的项目结构及其功能说明。
13. 让代码保持紧凑，每个子目录内代码文件数量尽可能保持在5个以内，每个尽量不超过1000行。
14. 确认完成改动后，在demo/目录下创建一个对应的示例程序。
15. 从项目之初就开始记录改动，留下人类可读可配置的日志。
16. 如果用户临时提出新要求，用`追加`开头作为标记并添加到下方。（e.g. 31. `追加`xxx）
17. 每实现一个小功能视作完成一个任务，此时立刻停下让用户检查，检查完成后由用户自行提交，你要给用户说明改动具体部分及作用，并 **用英文**给出一条言简意赅的提交信息。
18. 所有任务细则都会写在build_docs/plan/目录下，按照用户给出的路径阅读完功能说明文档再开工。
19. 在编写各类注释和文档时，无需特别强调你的操作源自于用户的什么请求。
20. 注释和文档必须使用表意完整，语义可理解的句子，禁止刻意缩字。
21. 在正式开工前，你需要在build_docs/blueprint目录下撰写你的功能实现蓝图，格式markdown，命名为`{plan文件名称}_phase{根据plan阶段标出数字}.md`描述你的代码结构，运作逻辑，可能存在的问题及其解决方案。蓝图中至少要包含trait、struct、函数签名和错误类型这些契约。你要把确定的内容写在蓝图里，其他无法抉择的部分直接与用户对话，由用户敲定后修订蓝图，直到问题完全解决且用户批准再写代码。
22. 由于计划文档在不断更新，你每次都需要重读用户指定的文档，以确保不落下任何要求。
23. 对于注释和文档，不允许自己生造名词来表示你所编写的逻辑或功能，你必须以常用名词来进行描述。同时，建议多打几个标点符号以确保表意清楚。以上内容可以简单理解为**禁止缩句，通俗表达**。以下是几个生硬句子和名词的修改：
  - 测试全绿。 -> 所有测试全部正常通过。
  - 设计语言模块根，汇总并再导出各令牌子模块。 -> 整合语言模块的文件。
  - 探测 macOS/Windows/Linux 系统中文字体追加为回退，失败静默降级。 -> 尝试查找 macOS/Windows/Linux 系统中文字体，如果失败，则默认恢复原样。
  - 一次装配深浅两套样式+字体。 -> 一次性完成深色和浅色两种外观样式和字体的加载。
  - 深浅 -> 深色和浅色外观模式
  - 均回 -> 均返回
  - 路由 -> 连接（近似于索引）
  - 分发器 -> `call_dmi`函数
  - 接线 -> 衔接（近似于适配）
24. 写文档时，自定义的结构体等代码块和逻辑机制保留英文原文并添加`号包裹，不要强行翻译成中文。
25. 避免使用比较生僻的概念（e.g. 管道向程序），如果一定要使用，请打一个括号并解释这个名词是什么意思。
26. 遇到以下两种情况，不要在原文档上强行修改，你要重写一份表述完整的文档，并且**不要强调发生修改**，直接当做原始设计来描述：
  - 询问设计层面问题后得到用户决策结果，试图将其加入蓝图；
  - 原设计被推翻，旧的文档表述过时，需要更新。
27. 编写文档时，不论是修改还是重写，在你想要说明新改动前，一定要检查你要描述的内容是否已经有成文表述，如果有，就在那段话上进行修改，而不是直接在一个部分下面不断添加新条目。
