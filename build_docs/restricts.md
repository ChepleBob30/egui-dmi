# 开发规范

1. 每次开工前，与用户确认实现方法、修改的文件、拿不准的实现细节这几点，待用户批准后再施工。
2. 每个方法、变量、字段等内容的命名不超过30个字符。
3. 为每一个方法和实现特定功能（e.g. 一个实现从指定路径获取并加载图片的方法中，你需要标出其文件查找与读取功能、适应图片尺寸功能等）的代码块添加不超过中文40字（英文按照中文翻译即可）的双语注释。
4. 尽可能减少临时存储型字段，多用变量处理，出现性能问题除外。
5. 在开始每一次任务前，你必须捋清项目结构，确认各个文件的代码风格，保持代码一致性。
6. 尽可能集中功能，不要将功能拆得特别散，方法少写几个。
7. 如果要创建文档，请放置在build_docs/changelog目录下。
8. 完成任务后，用人类能够理解的语言撰写一份修改报告，说明你改了哪几个文件，加了什么方法，对什么东西做了修改。
9. 无论做什么事情，一定要保留回退改动的余地。
10. **不要使用缩写。**
11. **不要替用户提交代码。**
12. 每次完成改动后，及时在build_docs/changelog添加新文件以及更新build_docs/structure.md的项目结构及其功能说明。
13. 让代码保持紧凑，每个子目录内代码文件数量尽可能保持在5个以内，每个尽量不超过1000行。
14. 确认完成改动后，在demo/目录下创建一个对应的示例程序。
15. 从项目之初就开始记录改动，留下人类可读可配置的日志。
16. 如果用户临时提出新要求，用`追加`开头作为标记并添加到下方。（e.g. 31. `追加`xxx）
17. 每实现一个小功能视作完成一个任务，此时立刻停下让用户检查，检查完成后由用户自行提交，你要给用户说明改动具体部分及作用，并给出一条言简意赅的提交信息。
18. 所有任务细则都会写在build_docs/plan/目录下，按照用户给出的路径阅读完功能说明文档再开工。
19. 在编写各类注释和文档时，无需特别强调你的操作源自于用户的什么请求。
20. 注释和文档必须使用表意完整，语义可理解的句子，禁止刻意缩字。
